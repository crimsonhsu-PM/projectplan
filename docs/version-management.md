# 版本管理規則

本專案使用 GitHub，因此合併申請稱為 PR；用途相當於 GitLab 的 MR。

## 日常流程

1. 從 GitHub 最新 `main` 建立 `codex/<改動名稱>` 分支。
2. 在分支完成一項可獨立驗收的功能、修正或文件更新，保留清楚的提交紀錄。
3. 執行適當檢查、更新變更紀錄，推送分支並建立 PR。大型改動可先建立草稿 PR。
4. 在 PR 說明功能、測試與限制，提供使用者可理解的驗收方式。
5. 等待使用者明確確認「合併」，檢查通過後以 squash merge 合併到 `main`。
6. 確認合併完成後，刪除已合併的功能分支。提交與 PR 歷史仍保留。
7. 要發布正式版本時，確認合併後的 `main` 檢查通過並完成驗收，再建立版本標籤。

不用等分支累積才建立 PR。彼此無關的改動分開處理；若有相依關係，先合併前置 PR，再讓後續分支更新到最新 `main`。

## 版本編號

採用三段式編號，標籤為 `v主版.次版.修訂版`。

| 情況 | 例子 |
| --- | --- |
| 第一個完成檢查與驗收的正式版本 | `v1.0.0` |
| 加入相容的新功能 | `v1.0.0` → `v1.1.0` |
| 修正錯誤、不改變相容性 | `v1.1.0` → `v1.1.1` |
| 不相容的重大改動或資料格式變更 | `v1.1.1` → `v2.0.0` |

每個 PR 不一定都要發布新版本。可以將多個已合併且驗收完成的 PR 整理成一個版本。版本編號以 Git tag 和 CHANGELOG 為準；不因加入版本管理文件而變更套件版本。

## 發布與驗收

- 程式變更執行適當的型別、靜態、單元、建置與操作流程檢查；目前 GitHub 工作流程已配置上述檢查。
- 純文件變更檢查文字、連結和格式；PR 仍應如實呈現 GitHub 檢查結果。
- 發布前確認使用者已驗收功能；測試失敗需先處理，不能以建立 Tag 取代檢查。
- 將 `CHANGELOG.md` 的待發布項目整理為版本、日期、功能、修正與已知限制。
- 在確認過的 `main` 提交建立 annotated tag，記錄版本說明，並推送該標籤至 GitHub。
- 已發布標籤永不移動或覆寫；後續修正使用新版本號。
- 建立 Tag、合併 PR 與部署網站是不同操作；需要網站部署時，另依使用者指示執行並驗證。

## 如何退回

### 想查看舊版

透過 GitHub 的 Tag 選擇版本即可查看當時原始碼。需要試跑時，從該 Tag 建立獨立分支，保留目前 `main`。

### 想撤銷某一項改動

從最新 `main` 建立 `codex/revert-<改動名稱>`，對該 PR 的 squash 提交執行 revert，完成相容性檢查與測試，再建立 PR 交由使用者確認合併。

### 想讓正式環境回到某個版本

先確認目標 Tag 和資料相容性。若只回退部署，可部署該 Tag 的程式；若也要讓 `main` 回復舊功能，另建立還原 PR，明確列出撤銷的改動、測試後再合併。還原後重新發布時使用新的版本號，不改寫舊標籤。

Git 只保存追蹤中的程式與文件，不備份 D1 資料、環境變數或使用者資料。資料庫變更需另外備份並設計相容或還原方案。

## 使用者如何交代

- 「新增人員匯出功能，做好後開 PR。」
- 「這個 PR 可以合併。」
- 「目前功能驗收完成，檢查通過後發布 v1.0.0。」
- 「幫我退回 baseline-20260820，先整理還原 PR 給我看。」

上述操作可由助理完成，不需要使用者親自操作 GitHub。

## 規則的執行範圍

`AGENTS.md` 與 PR 範本用來規範專案協作。它們不等同 GitHub 分支保護；本次未修改 GitHub Rulesets 或分支保護設定，因此平台仍可能允許具權限者直接推送 `main`。
